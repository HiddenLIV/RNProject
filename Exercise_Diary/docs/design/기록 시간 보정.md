# 기록 시간 보정 — 설계

스펙: `docs/specs/기록 시간 보정.md` (요구사항 1~9)

## 화면 구조

새 화면·컴포넌트 파일은 만들지 않는다. 보정 UI는 결과 화면 한 곳에서만 쓰이므로 `TimerScreen.tsx`의 `finished` 분기에 인라인으로 추가한다 (재사용처가 없는데 컴포넌트로 분리하면 과설계).

| 파일 | 역할 |
|---|---|
| `src/screens/TimerScreen.tsx` | (수정) `finished` 분기에 `−1초`/`+1초` 보정 버튼 추가. 정지 시 1초 이상이면 즉시 저장하고, 이후 보정마다 그 기록을 계속 갱신 |
| `src/lib/useHangTimer.ts` | 변경 없음 — `stop()`이 반환하는 `durationMs`를 그대로 사용 |
| `src/lib/storage.ts` | (수정) `updateRecord(id, patch)` 추가, 모든 쓰기(`addRecord`/`removeRecord`/`updateRecord`)를 한 큐로 직렬화 (아래 "쓰기 직렬화" 참고) |
| `src/lib/types.ts` | 변경 없음 |

## 상태 설계

> 최초 설계는 "정지 시 메모리에만 보관 → 결과 화면을 벗어날 때 커밋"이었고, 그다음 버전은 여기에 명시적 `기록 저장하기` 버튼을 더했다. 코드 리뷰에서 전자가 앱 강제 종료 시 보정 결과를 통째로 잃을 수 있다는 지적을 받아 "정지·보정마다 즉시 저장"으로 바꿨고, 그 결과 저장 버튼이 실제로 하는 일(저장)이 없어져 버튼 자체를 없앴다(2026-07-19). 지금은 `TimerScreen` 로컬 state 하나뿐이다.

- **`pending: PendingResult | null`** — 결과 화면에 표시 중인 값의 로컬 사본. `id` 필드로 "이미 저장된 기록"과의 연결을 추적한다: 정지 시 1초 이상이면 그 자리에서 `addRecord`로 저장하고 발급된 `id`를 담고, 아직 1초 미만이면 `id: null`(저장 대상 아님).

```ts
// TimerScreen.tsx 내부, export 하지 않는 로컬 타입
type PendingResult = {
  id: string | null; // 1초 이상이 되어 실제로 저장된 적이 있으면 그 기록의 id
  durationMs: number;
  measuredAt: string; // 실제 정지 시각(ISO) — 보정 중 시간이 흘러도 측정 일시는 정지 순간 그대로 유지
};
```

## 데이터 모델

`HangRecord`(`src/lib/types.ts`) 스키마는 변경 없음. 대신 `src/lib/storage.ts`에 부분 업데이트용 `updateRecord`를 추가한다.

```ts
export type HangRecord = {
  id: string;
  measuredAt: string;
  durationMs: number;

// src/lib/storage.ts
export function updateRecord(id: string, patch: Partial<HangRecord>): Promise<HangRecord[]>;
```

### 쓰기 직렬화

`addRecord`/`removeRecord`/`updateRecord`는 모두 `getRecords()` → `AsyncStorage.setItem()` 읽기-수정-쓰기라, 두 호출이 겹치면 나중에 끝난 쪽이 앞선 변경을 덮어써 기록을 잃을 수 있다. 세 함수를 모듈 스코프의 Promise 체인(`recordsQueue`)에 태워 항상 이전 쓰기가 끝난 뒤 다음 쓰기가 시작되도록 직렬화한다 — 개별 호출부마다 락을 신경 쓰지 않아도 되는 공용 메커니즘이다.

## 핵심 로직

1. **정지 시 1초 이상이면 즉시 저장** (요구사항 8) — `handleStop`은 `timer.stop()` 직후 `durationMs >= MIN_RECORD_MS`면 그 자리에서 `addRecord()`를 호출하고 발급된 `id`를 `pending`에 담는다. 1초 미만이면 저장하지 않고 `id: null`로만 보관한다(기존 "1초 미만 미저장" 규칙 그대로). `measuredAt`은 이 시점(정지 순간)에 캡처해 이후 사용자가 보정 버튼을 만지작거리는 동안에도 측정 일시가 밀리지 않게 한다.
   ```ts
   const handleStop = () => {
     const durationMs = timer.stop();
     stopAllSound();
     if (durationMs == null) return;
     const measuredAt = new Date().toISOString();
     if (durationMs >= MIN_RECORD_MS) {
       const id = createRecordId();
       addRecord({ id, measuredAt, durationMs });
       setPending({ id, durationMs, measuredAt });
     } else {
       setPending({ id: null, durationMs, measuredAt });
     }
   };
   ```

2. **±1초 보정은 ms 값에 그대로 ±1000을 더하고 빼며, 그 즉시 저장소도 함께 갱신한다** (요구사항 2, 3, 7) — "정수초만 바꾸고 소수점 이하는 유지"는 별도의 정수부/소수부 분리 로직이 필요 없다. `durationMs`가 34270(34.27초)일 때 −1000 = 33270(33.27초)이 정확히 요구사항과 일치한다. 밀리초 단위 산술이 자동으로 정수초 자리만 이동시킨다. 계산한 새 값이 1초 문턱을 넘나드는지에 따라 저장소 동작이 갈린다 — `pending.id`(이미 저장된 기록의 id 보유 여부)와 새 `durationMs`의 조합으로 새로 저장/기존 갱신/삭제를 판단:
   ```ts
   const adjustPending = (deltaMs: number) => {
     if (!pending) return;
     const durationMs = Math.max(0, pending.durationMs + deltaMs);
     if (durationMs >= MIN_RECORD_MS) {
       if (pending.id) {
         updateRecord(pending.id, { durationMs }); // 이미 저장된 기록을 그 값으로 갱신
         setPending({ ...pending, durationMs });
       } else {
         const id = createRecordId();
         addRecord({ id, measuredAt: pending.measuredAt, durationMs }); // 처음으로 1초 문턱을 넘음 → 새로 저장
         setPending({ ...pending, id, durationMs });
       }
     } else {
       if (pending.id) removeRecord(pending.id); // 1초 밑으로 다시 내려감 → 저장 대상에서 제외
       setPending({ ...pending, id: null, durationMs });
     }
   };
   ```
   보정은 결과 화면에 머무는 동안 몇 번이고 반복될 수 있는데, 매번 저장소에 반영해도 사용자 조작 빈도(±1초 탭)가 낮아 비용은 무시할 만한 수준이고, 그 대신 "메모리에만 있고 아직 저장 안 된" 구간이 사실상 없어진다(핵심 로직 4 참고).

3. **`−1초` 버튼 비활성화 조건** (요구사항 4) — "정수초 부분이 0"은 `pending.durationMs < MIN_RECORD_MS`와 같다. 이 조건에서 버튼을 `disabled`로 표시(투명도 낮춤 + `onPress` 무시). `+1초`는 상한 없이 항상 활성 (요구사항 5). 저장을 위해 보정을 잠글 필요가 없으므로(핵심 로직 1, 2에서 이미 실시간 저장됨) 그 외의 비활성화 조건은 없다.

4. **결과 화면 이탈 시 별도 커밋이 필요 없다** (요구사항 8) — 정지·보정 각각이 그 즉시 저장소에 반영되므로(핵심 로직 1, 2), `다시 시작`/`메인으로` 버튼과 화면 언마운트(탭 전환·뒤로가기)는 그냥 `timer.start(...)`/`timer.reset()`을 호출하면 된다 — 저장을 위해 별도로 가로챌 필요가 없다. 언마운트라는 React 생명주기 이벤트에 저장 여부가 달려있지 않으므로, 이 화면의 렌더링 방식이 나중에 바뀌어도(예: 탭을 언마운트 대신 `display:none`으로 유지하는 성능 최적화) 저장 로직이 조용히 깨질 걱정이 없다. **1초 미만으로 정지하고 한 번도 보정으로 문턱을 넘지 못한 경우만** 여전히 메모리에만 존재하며, 이는 원래 스펙상 "오조작으로 보고 저장하지 않는" 대상이라 앱 종료로 사라져도 회귀가 아니다.

## 의존성

추가 없음. 기존 React state와 `src/lib/storage.ts`만 사용한다.

## 구현 순서

1. `src/lib/storage.ts`에 쓰기 직렬화 큐와 `updateRecord` 추가 — 타입 체크 통과 확인.
2. `TimerScreen.tsx`에 `PendingResult`(`id` 포함) 타입, `pending` 상태 도입. `handleStop`을 1초 이상이면 즉시 `addRecord`, 미만이면 메모리 보관으로 변경.
3. `adjustPending`을 문턱 통과 여부에 따라 `addRecord`/`updateRecord`/`removeRecord`로 분기하도록 작성.
4. `finished` 분기 UI를 `pending.durationMs` 기준으로 표시 변경, `−1초`/`+1초` 버튼 추가(테마 토큰 사용, `−1초` 비활성화 조건은 `MIN_RECORD_MS` 상수 재사용).
5. `npx tsc --noEmit` + 실기기에서 시나리오 확인: 보정 후 값 표시 갱신, 0초 근처 비활성화, 정지 즉시(별도 조작 없이) 기록에 나타나는지, 1초 미만/이상 경계를 오갈 때 기록 목록에 나타났다 사라지는지, 앱을 강제 종료했다 다시 열어도 마지막 보정값이 남아있는지 → `/qa`로 스펙 성공 기준 전체 점검.
