# 데이터 백업 및 내보내기 — 설계

## 화면 구조

새 화면 신설 없음. 기존 홈 화면 헤더에 진입점 아이콘 하나와, 그 아이콘이 여는 모달 하나를 추가한다.

| 파일 | 역할 |
|---|---|
| `src/screens/HomeScreen.tsx` (수정) | 헤더에 백업 아이콘 버튼 추가, `BackupModal` 렌더링·상태 연결 |
| `src/components/BackupModal.tsx` (신규) | `HelpModal.tsx`와 동일한 전체화면 슬라이드 `Modal` 구조. "내보내기"/"가져오기" 두 행(각각 아이콘+제목+설명)을 보여주는 단순 선택 화면. 실제 파일 I/O·검증·확인 절차·성공/실패 피드백까지 이 컴포넌트 안에서 처리한다 |
| `src/lib/backup.ts` (신규) | 내보내기용 데이터 수집·파일 생성·공유 호출, 가져오기용 파일 선택·파싱·검증 — UI와 분리된 순수 로직 |
| `src/lib/storage.ts` (수정) | `restoreFromBackup()` 추가 — 기존 read-modify-write 큐를 재사용해 전체 교체를 한 번에 수행 |
| `src/lib/types.ts` (수정) | `BackupPayload` 타입, 스키마 버전 상수 추가 |
| `src/lib/i18n/locales/{ko,en,ja,zh}.ts` (수정) | `backup` 번역 섹션 추가 |

BackupModal 내부 레이아웃 (HelpModal과 동일한 헤더 재사용):

```
┌───────────────────────────────┐
│  ←(spacer)   백업/복원      ✕  │  ← HelpModal과 동일한 header 스타일
├───────────────────────────────┤
│  [↑] 내보내기                  │  ← Pressable row, HelpModal의 section 스타일 재사용
│      운동 기록을 파일로 저장    │
│                                │
│  [↓] 가져오기                  │
│      백업 파일로 복원           │
└───────────────────────────────┘
```

가져오기의 "정말 덮어쓸지" 확인과, 실패 사유 안내는 별도 커스텀 모달을 만들지 않고 React Native 기본 `Alert.alert`를 쓴다. 이유: RN의 `Modal`은 두 개가 동시에 `visible`이면(특히 iOS) 렌더링이 깨져서, `HomeScreen.tsx`에 이미 도움말↔온보딩 전환을 위한 `beginModalTransition` 지연 로직이 있다. `Alert.alert`는 RN Modal이 아닌 네이티브 다이얼로그라 이 문제와 무관하고, 파괴적 동작 확인이라는 목적에도 더 적합하다 — 새 상태 기계를 추가하지 않고 기존 문제를 피해간다.

## 상태 설계

**HomeScreen.tsx (기존 상태에 추가)**
- `backupVisible: boolean` — `helpVisible`/`onboardingVisible`와 같은 층위의 단순 토글.
- 기존 `modalTransitioning`과 함께, 헤더의 도움말 버튼과 백업 버튼은 서로 배타적으로 막는다:
  - 도움말 버튼: `disabled={modalTransitioning || backupVisible}`
  - 백업 버튼: `disabled={modalTransitioning || helpVisible || onboardingVisible}`
  - `BackupModal`은 내부에서 다른 RN `Modal`을 열지 않으므로(확인/에러는 `Alert.alert`), 도움말↔온보딩처럼 닫힘 애니메이션을 기다렸다가 다음 모달을 여는 체이닝 로직은 필요 없다. 단순 `onClose={() => setBackupVisible(false)}`로 충분하다.
- 가져오기 성공 시 `BackupModal`이 호출하는 `onRestored` 콜백에서 기존 `loadExercises()`를 재사용해 목록을 새로고침한다.

**BackupModal.tsx (로컬 상태)**
- `busy: 'idle' | 'exporting' | 'importing'` — 각 버튼을 누른 동안 중복 탭 방지 및 로딩 표시에 쓴다.
- `useAccentColors()`로 `setPresetId`를 가져와, 가져오기 성공 시 복원된 테마를 즉시 반영한다(기존 `ThemeContext`의 `setPresetId`가 상태 갱신 + 저장을 이미 처리하므로 그대로 재사용).
- 그 외 폼 상태 없음 — 파일 선택 결과나 파싱 결과는 `src/lib/backup.ts` 함수의 반환값/throw로만 오가며 컴포넌트에 별도로 보관하지 않는다.

## 데이터 모델

`src/lib/types.ts`에 추가:

```ts
export const BACKUP_SCHEMA_VERSION = 1;

// 운동별 기록·설정을 exercise.id로 묶어, 내부 AsyncStorage 키 네이밍(레거시 'hang' 특례 포함)이
// 백업 파일 형식에 그대로 노출되지 않게 한다 — storage.ts의 키 구조가 바뀌어도 백업 형식은 안정적이다.
export type BackupExerciseData = {
  records: TimeRecord[];
  repsRecords: RepsRecord[];
  settings: Settings;
};

export type BackupPayload = {
  schemaVersion: typeof BACKUP_SCHEMA_VERSION;
  exportedAt: string; // ISO 8601
  appVersion: string; // Constants.expoConfig?.version, 문제 리포트 시 참고용
  exercises: Exercise[];
  theme: ThemePresetId;
  exerciseData: Record<string /* exerciseId */, BackupExerciseData>;
};
```

## 핵심 로직

### 내보내기 (`src/lib/backup.ts`)

```ts
async function collectBackupPayload(): Promise<BackupPayload> {
  const exercises = await getExercises();
  const theme = await getThemePreset();
  const exerciseData: Record<string, BackupExerciseData> = {};
  await Promise.all(
    exercises.map(async (exercise) => {
      const [records, repsRecords, settings] = await Promise.all([
        getRecords(exercise.id),
        getRepsRecords(exercise.id),
        getSettings(exercise.id),
      ]);
      exerciseData[exercise.id] = { records, repsRecords, settings };
    }),
  );
  return {
    schemaVersion: BACKUP_SCHEMA_VERSION,
    exportedAt: new Date().toISOString(),
    appVersion: Constants.expoConfig?.version ?? 'unknown',
    exercises,
    theme,
    exerciseData,
  };
}

export async function exportBackup(): Promise<void> {
  const payload = await collectBackupPayload();
  const json = JSON.stringify(payload, null, 2);
  const fileName = `hiddenreps-backup-${formatStamp(payload.exportedAt)}.json`;
  const file = new File(Paths.cache, fileName);
  file.create({ overwrite: true });
  file.write(json);
  if (!(await Sharing.isAvailableAsync())) throw new BackupError('SHARE_UNAVAILABLE');
  await Sharing.shareAsync(file.uri, { mimeType: 'application/json', dialogTitle: fileName });
}
```

- `Paths.cache`(캐시 디렉터리)에 쓴다. 공유 시트로 다른 앱에 전달하는 용도일 뿐 앱이 영구 보관할 파일이 아니므로 시스템이 필요시 지워도 되는 캐시가 적합하다(`Paths.document`은 쓰지 않음).
- `Sharing.shareAsync()`가 resolve되는 시점은 Android에서 "공유 인텐트가 전달된 시점"이지 "상대 앱이 파일을 다 읽은 시점"이 아니다. 따라서 공유 직후 캐시 파일을 코드로 직접 삭제하지 않는다(삭제 경쟁 상태로 상대 앱이 빈 파일을 받는 사고를 피하기 위함). 파일명에 분 단위 타임스탬프가 들어가 내보낼 때마다(같은 분 안이 아니면) 캐시에 별개 파일이 남지만, 크기가 작고(수 KB) `Paths.cache`는 시스템이 필요시 정리하는 영역이라 별도 정리 로직을 두지 않는다. `overwrite: true`는 같은 분 안에 재시도할 때 파일명 충돌로 `create()`가 실패하는 것만 막는 용도다.
- `Constants`는 `expo-constants`(이미 설치돼 있음)에서 가져온다.

### 가져오기 (`src/lib/backup.ts`)

```ts
export async function pickBackupFile(): Promise<BackupPayload | null> {
  // MIME 필터를 'application/json'으로 좁히면 일부 안드로이드 파일 제공자(구글 드라이브 등)가
  // .json을 'application/octet-stream'으로 보고해 목록에서 안 보이는 경우가 있다 —
  // '*/*'로 열고 내용 기반으로 검증한다.
  const result = await DocumentPicker.getDocumentAsync({ type: '*/*', copyToCacheDirectory: true });
  if (result.canceled) return null;

  const text = await new File(result.assets[0].uri).text();
  let parsed: unknown;
  try {
    parsed = JSON.parse(text);
  } catch {
    throw new BackupError('INVALID_JSON');
  }
  if (!isBackupPayloadShape(parsed)) throw new BackupError('INVALID_SHAPE');
  if (parsed.schemaVersion !== BACKUP_SCHEMA_VERSION) throw new BackupError('UNSUPPORTED_VERSION');
  return parsed;
}
```

- `isBackupPayloadShape`는 얕은 검증만 한다: `schemaVersion`이 숫자인지, `exercises`가 배열인지, `exerciseData`가 객체인지, `exportedAt`이 문자열인지. 기존 `storage.ts`의 `readJson`도 저장된 JSON의 내부 필드까지 깊게 검증하지 않는 동일한 신뢰 수준을 쓰고 있어(예: `getExercises`는 배열 여부만 확인) 이와 일관성을 맞춘다. 스키마 검증 라이브러리(zod 등)는 이번 범위에 맞지 않는 과설계로 보고 추가하지 않는다.
- `BackupError`는 `{ code: 'SHARE_UNAVAILABLE' | 'INVALID_JSON' | 'INVALID_SHAPE' | 'UNSUPPORTED_VERSION' }` 정도의 최소 타입 — `BackupModal`이 `code`별로 `t.backup`의 다른 오류 문구를 골라 `Alert.alert`로 보여준다.
- 취소(`result.canceled`)는 에러가 아니라 `null` 반환 — 호출부는 아무 것도 하지 않고 조용히 끝난다(요구사항 11: 취소 시 부작용 없음).

### 복원 적용 (`src/lib/storage.ts`에 추가)

기존 `enqueueWrite` 직렬화 큐, `recordsKey`/`repsKey`/`settingsKey` 헬퍼를 그대로 재사용한다.

```ts
export function restoreFromBackup(payload: BackupPayload): Promise<void> {
  return enqueueWrite(async () => {
    const current = await getExercises();
    const staleKeys = current.flatMap((e) => [recordsKey(e.id), settingsKey(e.id), repsKey(e.id)]);
    if (staleKeys.length) await AsyncStorage.multiRemove(staleKeys);

    const entries: [string, string][] = [
      [EXERCISES_KEY, JSON.stringify(payload.exercises)],
      [THEME_KEY, JSON.stringify(payload.theme)],
    ];
    for (const exercise of payload.exercises) {
      const data = payload.exerciseData[exercise.id];
      if (!data) continue;
      entries.push([recordsKey(exercise.id), JSON.stringify(data.records)]);
      entries.push([repsKey(exercise.id), JSON.stringify(data.repsRecords)]);
      entries.push([settingsKey(exercise.id), JSON.stringify(data.settings)]);
    }
    await AsyncStorage.multiSet(entries);
  });
}
```

- 기존 데이터 삭제 → 새 데이터 기록 순서. AsyncStorage는 여러 키에 걸친 진짜 트랜잭션을 지원하지 않으므로 완벽한 원자성은 없다 — 다만 이는 기존 `removeExercise` 등도 이미 감수하고 있는 것과 같은 수준이라 이번에 새로 도입하는 약점이 아니다. 개인 운동 기록 앱 규모에서 이 이상의 트랜잭션 보장(임시 키 스와핑 등)은 과설계로 판단해 다루지 않는다.
- `BackupModal`은 `restoreFromBackup(payload)`가 끝나면 `accent.setPresetId(payload.theme)`(즉시 화면 반영 + 저장, 기존 로직 재사용)과 `onRestored()`(HomeScreen의 `loadExercises()` 트리거)를 호출한다 — 요구사항 10(재시작 없이 반영)을 앱 재시작 없이 만족.

### 타이머 관련

이번 기능은 시간 측정 로직을 다루지 않으므로 `Date.now()` 기반 계산 규칙과 무관하다. 백업에 포함되는 `TimeRecord.durationMs`는 이미 계산이 끝난 값을 그대로 직렬화·복원할 뿐이다.

## 의존성

| 패키지 | 이유 | 비고 |
|---|---|---|
| `expo-sharing` | OS 공유 시트로 백업 파일 전달 | SDK 57 기준 별도 config plugin 불필요(Android: "No additional set up necessary"). `npx expo install expo-sharing`으로 설치 |
| `expo-document-picker` | 백업 파일 선택(가져오기) | 일반적인 파일 선택엔 config plugin 불필요(iCloud 컨테이너 등 고급 옵션에만 필요, 이번 범위 아님). `npx expo install expo-document-picker`로 설치 |

이미 설치된 `expo-file-system`(새 `File`/`Paths` API, SDK 57에서 `writeAsStringAsync` 등 레거시 API는 `expo-file-system/legacy`로 옮겨졌고 기본 경로로 import 시 런타임 에러가 남 — 반드시 `import { File, Paths } from 'expo-file-system'` 사용)과 `expo-constants`(버전 정보)는 새로 추가하지 않고 그대로 재사용한다. 스키마 검증 라이브러리는 추가하지 않는다(위 참고).

## 구현 순서

1. `types.ts`에 `BackupPayload` 추가, `storage.ts`에 `restoreFromBackup()` 추가 → `npx tsc --noEmit`으로 타입만 우선 확인.
2. `npx expo install expo-sharing expo-document-picker` 후 `backup.ts`에 `collectBackupPayload`/`exportBackup` 작성 → 임시로 아무 버튼(또는 `HomeScreen`에 1줄짜리 임시 `onPress`)에 연결해 실기기/에뮬레이터에서 실제로 공유 시트가 뜨고 JSON이 전달되는지 확인.
3. `backup.ts`에 `pickBackupFile`/`isBackupPayloadShape` 작성 → 방금 만든 백업 파일을 다시 골라 파싱까지 되는지(아직 저장 반영 전) 로그로 확인. 형식이 다른 파일(예: 텍스트 파일)을 골라 `INVALID_JSON` 경로도 확인.
4. `BackupModal.tsx` 작성(내보내기/가져오기 버튼, `Alert.alert` 확인, `restoreFromBackup` 연동, 성공/실패 피드백) → `HomeScreen.tsx`에 아이콘·상태·상호 배타 처리 연결 → 전체 내보내기→가져오기 왕복이 실제로 데이터를 복원하는지 확인.
5. `ko/en/ja/zh` locale에 `backup` 섹션 채우기.
6. 스펙의 성공 기준 체크리스트를 하나씩 실기기/에뮬레이터로 검증(`/qa`).

## 스펙 요구사항 ↔ 설계 대응

| 스펙 요구사항 | 설계 반영 |
|---|---|
| 1. 홈 화면 상단 백업 아이콘 | `HomeScreen.tsx` 헤더에 버튼 추가 |
| 2. 내보내기/가져오기 선택 모달 | `BackupModal.tsx` |
| 3. 전체 데이터 포함 내보내기 | `collectBackupPayload()`가 exercises·records·repsRecords·settings·theme 전부 수집 |
| 4. 형식 버전 + 내보낸 일시 | `BackupPayload.schemaVersion`, `exportedAt` |
| 5. OS 공유 시트 전달 | `Sharing.shareAsync()` |
| 6. 영상은 참조 ID만 포함 | `TimeRecord`/`RepsRecord`의 `videoRef`를 그대로(가공 없이) 직렬화 — 원본 영상 파일 접근 코드 자체가 없음 |
| 7. 손상/형식불일치 시 오류, 기존 데이터 불변 | `pickBackupFile()`의 검증은 `restoreFromBackup()` 호출 이전에 전부 끝나 실패 시 저장소에 손대지 않음 |
| 8. 적용 전 확인 절차 | `Alert.alert` 확인/취소 |
| 9. 전체 교체(병합 아님) | `restoreFromBackup()`이 기존 per-exercise 키를 지우고 새 값으로 덮어씀 |
| 10. 재시작 없이 반영 | `onRestored()` → `loadExercises()`, `setPresetId()` → 즉시 상태 갱신 |
| 11. 취소 시 무변화 | `pickBackupFile()`이 취소 시 `null` 반환, 호출부는 아무 것도 하지 않음 |
