# 운동 촬영 영상 — 설계

스펙: `docs/specs/운동 촬영 영상.md` (요구사항 1~13)

## ⚠️ 사전 확인 — 안드로이드 마이크 권한 차단

`app.json`에 이미 `"blockedPermissions": ["android.permission.RECORD_AUDIO"]`가 설정돼 있다(오디오 재생만 하던 시절의 의도적 차단으로 보인다). 동영상 촬영은 오디오 트랙을 함께 녹화하는 게 기본 동작이라 마이크 권한이 필요한데, 이 설정이 남아있으면 안드로이드에서 카메라 촬영 자체가 실패하거나 크래시할 수 있다. **구현 1단계에서 이 항목을 `app.json`에서 제거해야 한다.** (무음 촬영으로 우회하는 방법은 없음 — `expo-image-picker`는 오디오 트랙 끄기 옵션을 제공하지 않는다.)

## 상태 설계

- **`TimerScreen`**: `capturedVideo: VideoRef | null` 로컬 state(초기 `null`). "이번 세션에서 찍은 영상"을 의미하며 `CaptureVideoRow`의 "방금 찍은 영상 보기" 표시 여부와 기록 연결에 동시에 쓰인다.
  - 촬영 성공 시: `setCapturedVideo(ref)`. 이미 저장된 기록이 있는 상태(`pending?.id`가 있음 — `finished` 단계에서 촬영한 경우)라면 그 자리에서 바로 `updateRecord`로 write-through한다.
  - `handleStop`에서 기록을 새로 만들 때(`durationMs >= MIN_RECORD_MS`) `videoRef: capturedVideo ?? undefined`를 함께 저장한다.
  - `adjustPending`에서 보정으로 새로 기록이 생성되는 분기(`pending.id`가 없다가 `+1초`로 새로 생기는 경우)도 동일하게 `capturedVideo`를 포함한다.
  - `handleRestart`(다시 시작)와 `handleGoMain`(메인으로)에서 `setCapturedVideo(null)` — 새 시도로 넘어가면 이전 촬영은 화면에서도, 다음 기록 연결 후보에서도 제외된다(요구사항 5의 취지를 타이머 화면에도 동일 적용).
  - `viewingVideo: boolean` — "방금 찍은 영상 보기"를 눌렀을 때 `VideoPlayerModal`을 열지 여부.
  - `permissionModal: PermissionState | null` — `null`이면 모달 숨김, 그 외엔 `CameraPermissionModal`이 뜨고 상태에 맞는 버튼을 보여준다(핵심 로직 3).
  - `busy: boolean` — 권한 확인 시작부터 촬영·저장이 끝날 때까지 `true`. `CaptureVideoRow`에 그대로 전달돼 중복 탭을 막는다.
- **`RepsScreen`**: `capturedVideo: VideoRef | null` 동일한 의미. `handleSave` 성공 후 `setSets([newSet()])`와 같은 타이밍에 `setCapturedVideo(null)`로 초기화(기존 "세트 초기화" 패턴과 동일한 자리).
  - 저장하지 않고 화면을 벗어나면(탭 전환·뒤로 가기) `ExerciseScreen`의 조건부 렌더링으로 `RepsScreen`이 언마운트되어 `capturedVideo`가 그냥 사라진다 — `GuideVideoPanel` 설계와 같은 이유로 별도 정리 로직이 필요 없다(요구사항 5).
  - `viewingVideo: boolean`, `permissionModal: PermissionState | null`, `busy: boolean` — `TimerScreen`과 동일.
- **`RecordsScreen`**(의 `TimeRecordsScreen`/`RepsRecordsScreen` 각각): `viewingAssetId: string | null` — 목록에서 영상 아이콘을 탭하면 그 기록의 `videoRef.assetId`를 넣고, `VideoPlayerModal`이 이를 받아 재생한다.
- **`CaptureVideoRow`**: 상태 없음(순수 프레젠테이션) — `capturedAssetId`, `busy`, `onCapture`, `onViewCaptured` props만 받는다. `busy`는 호출부(TimerScreen/RepsScreen)가 촬영 처리 중(카메라 실행 ~ 갤러리 저장 완료) 동안 `true`로 둬서 중복 탭을 막는다.
- **`VideoPlayerModal`**: `uri: string | null | undefined` 내부 state(`undefined`=조회 중, `null`=못 찾음, `string`=재생 가능). `assetId` prop이 바뀔 때마다 `resolveVideoUri`를 다시 호출.

## 데이터 모델

```ts
// src/lib/types.ts
export type VideoRef = {
  assetId: string; // expo-media-library Asset.id — 기기 갤러리 상의 영상을 가리키는 참조. 영상 파일 자체는 앱이 보관하지 않는다.
};

export type TimeRecord = {
  id: string;
  measuredAt: string;
  durationMs: number;
  videoRef?: VideoRef;
};

export type RepsRecord = {
  id: string;
  measuredAt: string;
  sets: RepsSet[];
  weightUnit?: 'kg' | 'lb';
  videoRef?: VideoRef;
};
```

`assetId` 하나만 저장한다 — 실제 재생 가능한 로컬 경로(`localUri`)는 플랫폼·시점에 따라 바뀔 수 있어서 저장해두지 않고, 재생할 때마다 `expo-media-library`로 다시 조회한다(요구사항 9의 "삭제됐으면 못 찾는다는 안내"도 이 조회 시점에 자연스럽게 처리된다).

## 핵심 로직

1. **권한 상태 조회·요청** (요구사항 11~13) — `src/lib/video.ts`. OS 권한 팝업을 실제로 띄우는 함수(`request*`)와, 팝업 없이 현재 상태만 읽는 함수(`get*`)를 분리한다 — 안내 모달을 띄울지 말지 판단은 팝업을 유발하지 않아야 하기 때문이다.
   ```ts
   export type PermissionState = 'undetermined' | 'denied' | 'blocked'; // 'blocked' = 영구 거부(canAskAgain: false)

   export async function getVideoPermissionState(): Promise<PermissionState | 'granted'> {
     const camera = await ImagePicker.getCameraPermissionsAsync();
     const library = await MediaLibrary.getPermissionsAsync();
     if (camera.granted && library.granted) return 'granted';
     if (camera.canAskAgain === false || library.canAskAgain === false) return 'blocked';
     if (camera.status === 'undetermined' || library.status === 'undetermined') return 'undetermined';
     return 'denied';
   }

   export async function requestVideoPermissions(): Promise<boolean> {
     const camera = await ImagePicker.requestCameraPermissionsAsync();
     const library = await MediaLibrary.requestPermissionsAsync();
     return camera.granted && library.granted;
   }
   ```
   `canAskAgain: false`는 iOS·안드로이드 모두 "사용자가 거부했고 OS가 더 이상 팝업을 안 띄워주는" 상태를 가리키는 공통 필드라, 이 값 하나로 "권한 허용" 버튼과 "설정으로 이동" 버튼을 가를 수 있다.

2. **촬영 → 갤러리 저장** (요구사항 2~3) — 같은 파일. 이 함수는 **권한이 이미 있다는 전제로만** 호출된다(권한 확보는 화면 쪽 오케스트레이션에서 먼저 끝낸다):
   ```ts
   import { Asset } from 'expo-media-library';

   export type VideoCaptureResult = { status: 'saved'; ref: VideoRef } | { status: 'cancelled' };

   export async function captureExerciseVideo(): Promise<VideoCaptureResult> {
     const result = await ImagePicker.launchCameraAsync({ mediaTypes: ['videos'] });
     if (result.canceled || !result.assets?.[0]) return { status: 'cancelled' };

     const tempUri = result.assets[0].uri;
     const asset = await Asset.create(tempUri);
     await FileSystem.deleteAsync(tempUri, { idempotent: true }); // 앱 캐시에 남은 원본 정리 — "앱은 영상을 보관 안 함"을 실제로 보장
     return { status: 'saved', ref: { assetId: asset.id } };
   }
   ```
   `Asset.create`가 갤러리에 실제 항목을 만들고, 카메라가 반환한 캐시 파일은 즉시 지워서 앱 쪽엔 아무 사본도 남지 않는다(요구사항 3).
   > **설계 변경 (구현 중 발견)**: SDK 57의 `expo-media-library`는 예전 정적 함수(`createAssetAsync`/`getAssetInfoAsync` 등)를 새로운 클래스 기반 API(`Asset`/`Album`/`Query`)로 교체했다. 기존 함수들은 메인 패키지에서 호출하면 "This method will throw in runtime"이라고 명시된 사실상 삭제된 API라 그대로 쓸 수 없다(`expo-media-library/legacy`에서 import하면 여전히 되지만, SDK가 명시적으로 폐기 예고한 경로라 쓰지 않는다). `requestPermissionsAsync`/`getPermissionsAsync`는 최상위 함수로 그대로 남아있어 권한 쪽 설계는 변경 없음.
   > **설계 변경 (실기기 테스트 중 발견 1)**: `getPermissionsAsync`/`requestPermissionsAsync`에 `granularPermissions` 인자를 안 넘기면 기본값(`['photo','video','audio']`)이 적용돼, 안드로이드 13+ 실기기에서 사진뿐 아니라 "기기의 음악과 오디오" 접근까지 별도 권한 팝업으로 물어본다 — 영상만 다루는 이 기능엔 불필요하고 사용자에게 혼란을 준다. `LIBRARY_GRANULAR_PERMISSIONS = ['video']`로 고정해서 세 함수(`getVideoPermissionState`/`requestVideoPermissions`/`resolveVideoUri`) 모두 이 값을 넘기도록 수정. `app.json`의 `expo-media-library` 플러그인 옵션에도 `"granularPermissions": ["video"]`를 추가해 매니페스트에도 불필요한 권한이 안 실리게 함.
   > **설계 변경 (실기기 테스트 중 발견 2)**: 원래 `runCapture`(핵심 로직 3)에 예외 처리가 없어서, 카메라 촬영 후 `Asset.create`/`FileSystem.deleteAsync` 과정에서 문제가 생기면 `videoBusy`가 `true`로 영구히 남아 "처리 중" 버튼이 안 풀리는 버그가 실기기에서 실제로 재현됐다(요구사항 10의 "앱이 멈추지 않는다"를 어김). `try { ... } catch { Alert.alert(...) } finally { setVideoBusy(false) }`로 감싸 항상 busy 상태가 풀리고, 실패 시 안내가 뜨도록 수정.
   > **설계 변경 (실기기 테스트 중 발견 3)**: 위 수정 이후 실기기에서 "갤러리엔 저장되는데 앱은 촬영 실패로 처리한다"는 증상이 재현됐다 — `Asset.create(tempUri)`(갤러리 저장)는 성공하지만, 뒤이은 `FileSystem.deleteAsync(tempUri, { idempotent: true })`가 예외를 던져 전체 함수가 실패로 끝나면서 `{ status: 'saved', ref }`를 반환하지 못했던 것으로 보인다. 삭제 호출만 별도 `try/catch`로 감싸 실패를 무시하고 저장 성공 여부와는 분리했다.
   > **설계 변경 (`/qa` 중 발견 4, 원인 정정)**: 발견 3의 원인 추정("권한·경로 문제")은 틀렸다 — `expo-file-system`도 SDK 57에서 `expo-media-library`와 같은 방식으로 API가 개편됐고, 메인 엔트리(`import ... from 'expo-file-system'`)의 `deleteAsync`는 `expo-media-library`의 예전 함수들과 동일하게 "호출하면 무조건 throw하는 경고 스텁"이다(`node_modules/expo-file-system/src/legacyWarnings.ts`). 즉 발견 3에서 추가한 `try/catch`는 예외 자체는 잘 삼켰지만, **삭제가 원천적으로 한 번도 성공한 적이 없어 촬영마다 앱 캐시에 영상 원본이 계속 쌓이고 있었다** — 요구사항 3 위반. 새 클래스 기반 API로 교체: `import { File } from 'expo-file-system'` → `new File(tempUri)`의 `exists` 확인 후 `delete()`(동기 메서드) 호출. `try/catch`는 그대로 유지(파일이 이미 없는 경우 등 대비).
   > **버그 수정 (`/qa` 중 발견, 세 가지 경미한 문제)**:
   > 1. `VideoPlayerModal`을 닫아도(`assetId → null`) 기존에는 `useEffect`가 `if (!assetId) return;`으로 조기 반환해 `uri` state가 초기화되지 않았다 — `useVideoPlayer`는 source가 바뀔 때만 플레이어를 재생성·해제하므로, 재생 중 닫으면 플레이어가 살아남아 소리가 계속 날 수 있었다. `assetId`가 없어졌을 때도 `uri`를 `undefined`로 리셋하도록 수정해, 플레이어가 null 소스로 재생성되며 이전 플레이어가 해제되게 했다.
   > 2. `handleCapturePress`가 권한 조회(`await getVideoPermissionState()`)를 하는 동안 `videoBusy`가 아직 `true`로 안 바뀌어 있어, 그 사이 연타하면 `launchCameraAsync`가 중복 호출될 수 있었다 — 함수 맨 앞에서 `if (videoBusy) return;` 가드 후 즉시 `setVideoBusy(true)`로 재진입 창을 없앴다(권한 모달로 빠지는 분기에서는 다시 `setVideoBusy(false)`로 되돌림).
   > 3. `requestVideoPermissions`가 카메라 권한을 거부당해도 갤러리 권한 팝업을 이어서 띄웠다 — 카메라가 거부되면 곧바로 `false`를 반환하도록 해서 불필요한 팝업 하나를 없앴다.

3. **화면에서의 권한 흐름 오케스트레이션** (요구사항 1, 11~13) — `TimerScreen`/`RepsScreen`에 공통으로 들어가는 로직(중복되지만 두 화면 모두 짧아서 별도 훅으로 뽑지 않는다):
   ```ts
   const handleCapturePress = async () => {
     const state = await getVideoPermissionState();
     if (state !== 'granted') {
       setPermissionModal(state); // CameraPermissionModal이 뜬다
       return;
     }
     await runCapture();
   };

   const runCapture = async () => {
     setBusy(true);
     const result = await captureExerciseVideo();
     setBusy(false);
     if (result.status !== 'saved') return;
     setCapturedVideo(result.ref);
     if (pending?.id) updateRecord(exercise.id, pending.id, { videoRef: result.ref }); // TimerScreen만 해당
   };

   const handleGrantPermission = async () => {
     const granted = await requestVideoPermissions();
     if (!granted) {
       setPermissionModal(await getVideoPermissionState()); // 거부/영구거부 상태로 갱신 — 모달은 열린 채 버튼만 바뀔 수 있다
       return;
     }
     setPermissionModal(null);
     await runCapture();
   };
   ```
   요구사항 13(이미 허용한 사용자는 안내 페이지를 안 본다)은 `getVideoPermissionState()`가 `'granted'`를 반환하는 순간 `runCapture()`로 바로 넘어가는 이 분기 하나로 충족된다.

4. **재생용 URI 조회** (요구사항 6~9) — `src/lib/video.ts`:
   ```ts
   import { Asset, getPermissionsAsync } from 'expo-media-library';

   export async function resolveVideoUri(assetId: string): Promise<string | null> {
     try {
       const permission = await getPermissionsAsync(); // 조회만, OS 팝업 유발 안 함
       if (!permission.granted) return null;
       const asset = new Asset(assetId);
       return await asset.getUri(); // 에셋이 삭제됐으면 이 호출이 reject됨 → catch에서 null로 수렴
     } catch {
       return null;
     }
   }
   ```
   실패(권한 없음·에셋 삭제됨·예외 발생) 시 전부 `null`로 수렴시켜 `VideoPlayerModal`이 "영상을 찾을 수 없습니다" 한 가지 상태로만 처리하면 되게 한다. 여기서는 `request*`가 아니라 `get*`(조회 전용)를 쓴다 — 오래된 기록의 영상을 볼 때(예: 권한을 나중에 껐다 켰다 한 경우) 목록을 탭하는 것만으로 예상치 못한 OS 권한 팝업이 뜨는 걸 막기 위해서다.

5. **`CameraPermissionModal` UI** (요구사항 11~13):
   ```tsx
   type Props = {
     state: PermissionState | null; // null이면 렌더링 안 함
     onGrant: () => void;
     onOpenSettings: () => void;
     onClose: () => void;
   };
   export default function CameraPermissionModal({ state, onGrant, onOpenSettings, onClose }: Props) {
     if (!state) return null;
     const blocked = state === 'blocked';
     return (
       <Modal visible transparent animationType="fade" onRequestClose={onClose}>
         <View style={styles.backdrop}>
           <View style={styles.card}>
             <Text style={styles.title}>카메라·사진 접근 권한이 필요해요</Text>
             <Text style={styles.body}>
               운동하는 모습을 촬영하고 기기 갤러리에 저장하려면 카메라와 사진 접근 권한이 필요합니다.
             </Text>
             <Pressable style={styles.primaryButton} onPress={blocked ? onOpenSettings : onGrant}>
               <Text style={styles.primaryButtonText}>{blocked ? '설정으로 이동' : '권한 허용'}</Text>
             </Pressable>
             <Pressable style={styles.secondaryButton} onPress={onClose}>
               <Text style={styles.secondaryButtonText}>취소</Text>
             </Pressable>
           </View>
         </View>
       </Modal>
     );
   }
   ```
   `onOpenSettings`은 화면 쪽에서 `Linking.openSettings()`를 호출한다(React Native 내장 API, 별도 패키지 불필요). 설정에서 돌아온 뒤 자동으로 재확인하지는 않는다 — 사용자가 촬영 버튼을 다시 누르면 그때 `getVideoPermissionState()`가 최신 상태를 다시 읽으므로, 권한을 켜고 왔다면 다음 탭에서 바로 카메라가 열린다(요구사항 13과 동일한 경로).

6. **세션→기록 연결** (요구사항 4~5) — `TimerScreen`/`RepsScreen`의 상태 설계에서 다룬 대로, "촬영은 로컬 state에 쌓이고, 레코드가 실제로 저장되는 시점(또는 이미 저장된 레코드가 있으면 그 즉시)에 흘러 들어간다"는 한 가지 규칙으로 두 화면 모두 처리한다. 두 화면의 차이는 "레코드가 언제 생기는가"뿐이다:
   - `RepsScreen`: 명시적 "기록 저장" 버튼을 눌러야 레코드가 생긴다 → `capturedVideo`는 그 저장 호출에만 실리면 된다.
   - `TimerScreen`: 정지하는 순간 자동으로 레코드가 생긴다(1초 미만이면 생기지 않고, `+1초` 보정으로 나중에 생길 수도 있다) → `capturedVideo`가 레코드보다 먼저 있을 수도, 나중에 있을 수도 있어서 "레코드 존재 여부"에 따라 `addRecord`에 실어 보내거나 `updateRecord`로 write-through한다.

7. **재생 UI** (요구사항 6~7) — `VideoPlayerModal`:
   ```tsx
   export default function VideoPlayerModal({ assetId, onClose }: Props) {
     const [uri, setUri] = useState<string | null | undefined>(undefined);
     useEffect(() => {
       if (!assetId) return;
       let cancelled = false;
       setUri(undefined);
       resolveVideoUri(assetId).then((r) => { if (!cancelled) setUri(r); });
       return () => { cancelled = true; };
     }, [assetId]);
     const player = useVideoPlayer(uri ?? null, (p) => p.play());

     if (!assetId) return null;
     return (
       <Modal visible transparent animationType="fade" onRequestClose={onClose}>
         <View style={styles.backdrop}>
           <View style={styles.card}>
             <Pressable style={styles.closeButton} onPress={onClose} hitSlop={8}>
               <Ionicons name="close" size={22} color={colors.text} />
             </Pressable>
             {uri === undefined && <ActivityIndicator color={colors.primary} />}
             {uri === null && <Text style={styles.notFound}>영상을 찾을 수 없습니다</Text>}
             {uri && <VideoView player={player} style={styles.video} nativeControls />}
           </View>
         </View>
       </Modal>
     );
   }
   ```
   `EditExerciseModal`과 같은 `Modal transparent + backdrop + card` 패턴을 그대로 따른다.

8. **`TimerScreen` 레이아웃 조정** — 지금은 `phase`별 블록이 `justifyContent:'center'`인 컨테이너에 조건부로 바로 들어가 있다. `CaptureVideoRow`는 모든 phase에서 보여야 하므로, 컨테이너를 상단 고정 바(`CaptureVideoRow`) + 기존 phase 콘텐츠(별도 `flex:1, justifyContent:'center'` 래퍼로 이동)로 나눈다. 기존 화면의 중앙 정렬 결과물은 그대로 유지된다.

## 의존성

- `expo-image-picker` — 카메라 촬영. `npx expo install expo-image-picker`
- `expo-media-library` — 갤러리에 저장하고, 나중에 그 위치를 다시 조회. `npx expo install expo-media-library`
- `expo-video` — 저장된 영상 재생(`useVideoPlayer` + `VideoView`). `npx expo install expo-video`
- `expo-file-system` — 촬영 직후 앱 캐시에 남은 임시 파일 삭제. 이미 다른 expo 패키지의 전이 의존성으로 설치돼 있지만(package-lock.json에 존재, package.json엔 없음), 직접 쓰므로 `npx expo install expo-file-system`으로 명시적 의존성으로 올린다.
- **`app.json` 수정 필요**:
  - `android.blockedPermissions`에서 `"android.permission.RECORD_AUDIO"` 제거(사전 확인 항목 참고).
  - `plugins`에 `expo-image-picker`(카메라 사용 설명), `expo-media-library`(사진 라이브러리 접근 설명) 추가하고 iOS 권한 설명 문자열(`NSCameraUsageDescription`, `NSMicrophoneUsageDescription`, `NSPhotoLibraryUsageDescription`/`NSPhotoLibraryAddUsageDescription`)을 채운다. 정확한 플러그인 옵션 키는 SDK 57 문서로 확인 필요(AGENTS.md 지침).
- **확인 필요**: `expo-video`가 이 프로젝트의 신규 아키텍처(RN 0.86)에서 그대로 동작하는지 — 설치 직후 아무 로컬 영상 파일이나 하드코딩해 `VideoPlayerModal` 최소 렌더링을 실기기에서 먼저 확인한다(자세 영상 기능 때 `react-native-youtube-iframe`에 대해 했던 것과 같은 이유).

## 구현 순서

각 단계 끝에서 기존 기능(타이머·세트 기록·자세 영상)이 깨지지 않았는지 확인한다.

1. **권한·의존성 정리 + 최소 파이프라인 확인** — `app.json`에서 `RECORD_AUDIO` 차단 제거, 세 패키지 설치 + 플러그인 설정 → `npx expo prebuild --clean`으로 네이티브 프로젝트 재생성(이름 변경 때처럼 캐시 문제를 피하려면 이 방법이 제일 확실 — 메모리 기록 참고) → 실기기에서 "촬영 버튼 하나만 있는 임시 화면"으로 촬영→갤러리 저장→`resolveVideoUri`→재생까지 엔드투엔드로 한 번 확인한다. 이 프로젝트에서 가장 리스크가 큰 구간이라 가장 먼저 검증한다. 이 단계에서 앱을 완전히 지우고 재설치해 "권한을 한 번도 물어본 적 없는 상태"부터 실제로 확인한다(권한은 한 번 허용/거부하면 같은 설치본에서는 재현이 안 됨).
2. **데이터 계층** — `types.ts`에 `VideoRef`, `TimeRecord`/`RepsRecord`에 `videoRef?` 추가. `src/lib/video.ts` 정식 작성(권한 함수 포함). 타입 체크.
3. **재생 컴포넌트** — 1번의 임시 코드를 `VideoPlayerModal`로 정식화.
4. **`CameraPermissionModal` 컴포넌트** — `undetermined`/`denied`/`blocked` 세 상태의 버튼·문구가 각각 맞게 나오는지 임시로 상태를 하드코딩해 먼저 확인.
5. **`CaptureVideoRow` + 권한 오케스트레이션 + `TimerScreen` 연동** — 레이아웃 조정, `capturedVideo`/`permissionModal`/`busy` 상태, `addRecord`/`updateRecord`/`adjustPending` 세 지점에 연결, 재시작 시 초기화까지 확인.
6. **`RepsScreen` 연동** — `CaptureVideoRow` + 권한 오케스트레이션 배치, 저장 시 연결 + 세트 초기화와 같이 리셋.
7. **`RecordsScreen`/`RecordItem`/`RepsRecordItem` 연동** — 영상 아이콘 노출, 탭하면 `VideoPlayerModal` 오픈, 기록 삭제 후 갤러리 파일이 남아있는지 확인.
8. `npx tsc --noEmit` + 실기기 확인(카메라·갤러리 권한 흐름은 시뮬레이터로 확인 안 되는 부분이 많아 실기기 필수) → `/qa`.
