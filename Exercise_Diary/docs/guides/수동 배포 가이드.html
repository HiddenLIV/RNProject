나의 운동 일지 — 수동 배포 가이드 (업데이트)

스토어 자동 배포(CI)없음.github/workflows/exercise-diary-ci.yml은 타입체크·유닛테스트·린트만 수행 — 빌드/제출은 항상 수동

즉 지금 "배포"는 예외 상황이 아니라 유일한 경로다 — 자동 배포 파이프라인이 없으므로, 새 버전을 사용자에게 전달하는 방법은 이 문서의 절차뿐이다.

01

언제 이 문서를 쓰나

버그 수정, 새 기능, 텍스트/디자인 변경 등 어떤 종류의 변경이든 — main 브랜치에 반영된 코드를 실제 사용자에게 전달하려면 이 절차를 거쳐야 한다. "코드만 고치고 커밋·푸시"까지는 저장소 상태만 바꿀 뿐, 스토어에 설치된 앱은 전혀 바뀌지 않는다.

02

사전 확인

터미널
npx eas-cli whoami          # 로그인 계정 확인 (0hiddenlab1@gmail.com)
git status                   # 배포하려는 커밋이 실제로 반영돼 있는지 확인
ls hiddenlabs-*.json         # Play 서비스 계정 키 파일 존재 확인 (.gitignore 처리됨, 커밋 안 됨)

이 저장소 환경에서는 npx eas ...가 "could not determine executable" 오류로 실패한다. 반드시 패키지명을 명시한 npx eas-cli ...를 쓴다.

03

버전 올리기

app.json의 expo.version을 새 값으로 올린다. Android versionCode/iOS buildNumber는 eas.json의 appVersionSource: "remote" + build.production.autoIncrement: true 덕분에 EAS가 자동으로 관리하므로 손댈 필요 없다.

app.json
"version": "1.0.7"   // 예: 1.0.6 → 1.0.7
04

빌드

Android

EAS Build

터미널
# 로컬 빌드 — 이 맥에 Java/Android SDK/NDK가 있어 큐 대기 없이 즉시 진행 (권장)
npx eas-cli build --platform android --profile production --local --non-interactive --output ./build-production.aab

# 또는 클라우드 빌드 — Free 플랜은 큐 대기가 있을 수 있음
npx eas-cli build --platform android --profile production --non-interactive
iOS

아직 해당 없음

iOS는 최초 스토어 등록 전이라 이 "업데이트" 절차의 대상이 아니다. 최초 배포를 시작하려면 앱스토어 배포 가이드.html을 먼저 따른다 (단, 그 문서는 2026-08-10 기준 초안이라 eas.json·계정 상태를 실행 전에 다시 확인할 것).

05

제출

터미널
npx eas-cli submit --platform android --profile production --path ./build-production.aab --non-interactive

eas.json의 submit.production.android.track이 "production"이므로 프로덕션 트랙으로 바로 올라간다. 단 releaseStatus: "draft"가 남아있으면 Play Console에서 수동으로 "검토를 위해 전송"을 눌러야 실제 배포된다 — 이 값이 왜 남아있는지, 최근 업데이트에서도 필요한지는 실제 제출 결과를 보고 판단한다 (최초 배포 때는 신규 계정 심사 대기로 인한 임시 조치였다).

06

구버전 사용자에게 업데이트 안내 띄우기

스토어 배포와 앱 내 "업데이트 안내 바텀시트"는 서로 다른 이벤트다. 이 안내(src/lib/forceUpdate.ts)는 docs/version.json의 minVersion과 설치된 버전을 비교해서만 뜬다 — 03단계에서 app.json만 올리고 이 단계를 빠뜨리면 기존 사용자는 새 버전이 나온 걸 전혀 알 수 없다.

  1. 이번 릴리스가 구버전 사용자에게 꼭 업데이트를 유도해야 하는 릴리스인지 판단한다 (버그 픽스·중요 변경이면 예, 사소한 개선이면 생략 가능).
  2. docs/version.json의 android.minVersion을 방금 배포한 app.json의 version 값으로 올린다.
  3. gh-pages 브랜치를 git worktree add로 임시 워크트리에 연결해, 그 워크트리의 version.json에 같은 내용을 반영·커밋·푸시한다 (docs/privacy-policy.html 배포와 같은 방식). 현재 로컬에 상시 워크트리는 없으므로 매번 새로 붙였다 정리한다.
  4. gh-pages 응답에 cache-control: max-age=600이 있어 재배포 직후 최대 10분은 CDN에 이전 값이 남을 수 있다.

이 저장소 규칙 — 배포를 요청받으면 사용자에게 다시 물어보지 않고 docs/version.json 갱신과 gh-pages 재배포까지 항상 함께 진행한다.

07

주의 — OTA(EAS Update) 아직 미설정

expo-updates 패키지가 프로젝트에 설치돼 있지 않다. 즉 npx eas-cli update --branch production 같은 OTA 배포는 현재 이 프로젝트에서 동작하지 않는다 — 텍스트 한 줄, 색상 하나만 바뀐 경우에도 04·05단계(전체 재빌드 + 재제출 + 스토어 재심사)를 그대로 거쳐야 한다. OTA를 도입하려면 별도로 expo-updates 설치와 runtimeVersion/채널 설정이 선행돼야 하며, 이는 이 문서의 범위 밖이다.
