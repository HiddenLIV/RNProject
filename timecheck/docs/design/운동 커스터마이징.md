# 운동 커스터마이징 — 설계

스펙: `docs/specs/운동 커스터마이징.md` (요구사항 1~19)

## 핵심 아이디어: 마이그레이션 없는 통합

지금 매달리기 기록은 `timecheck:records:v1`, 설정은 `timecheck:settings:v1`라는 고정 키로 저장돼 있다. 이 키들의 의미를 그대로 유지한 채, "매달리기"를 `id: 'hang'`인 내장 운동으로 취급하고, **운동 id가 `'hang'`이면 항상 이 기존 키를 그대로 쓰도록** 저장소 함수를 설계한다. 새로 추가되는 운동만 `id` 기반의 새 키(`timecheck:records:<id>:v1`)를 받는다. 이렇게 하면 기존 데이터를 옮기는 마이그레이션 스크립트가 전혀 필요 없다 — 요구사항 19(기존 기록 유실 없이 유지)가 설계 자체로 보장된다.

## 상태 설계

- **운동 목록**: `HomeScreen`의 로컬 state, 마운트 시 `getExercises()`로 로드 (기존 `RecordsScreen`이 기록을 로드하던 것과 같은 패턴). 홈으로 돌아올 때마다 `App.tsx`의 조건부 렌더링으로 `HomeScreen`이 다시 마운트되므로 별도의 "포커스 시 새로고침" 로직 없이 항상 최신 목록을 본다 (기존 탭 전환 방식과 동일한 이유).
- **`App.tsx`의 화면 상태**: `type Screen = { name: 'home' } | { name: 'exercise'; exercise: Exercise } | { name: 'addExercise' }`. `exerciseId`가 아니라 `Exercise` 객체 자체를 들고 있다 — `HomeScreen`이 이미 로드해 둔 객체를 그대로 넘겨 재조회를 피한다는 의도를 타입에도 그대로 반영했다(구현 중 확정). `HomeScreen`의 `onSelectExercise(exercise)` → `{ name: 'exercise', exercise }`, "운동 추가" 카드 → `{ name: 'addExercise' }`.
- **`ExerciseScreen`**: `exercise: Exercise`를 prop으로 받는다 (id로 다시 조회하지 않고, `HomeScreen`이 이미 들고 있던 객체를 그대로 넘긴다 — 별도 조회 왕복 불필요). 내부 탭 상태(`'measure' | 'records'`)는 기존 `HangScreen`의 `tab` state와 동일.
- **`TimerScreen`/`RecordsScreen`**: 기존처럼 각자 로컬 state로 설정·기록을 관리하되, 저장소 호출 시 `exercise.id`를 인자로 넘긴다.
- **`AddExerciseScreen`**: 로컬 state로 입력 중인 이름·선택된 측정방식·무게 사용 여부·단위를 관리. 저장 성공 시 `onCreated()` 콜백으로 `App.tsx`에 알려 홈으로 돌아간다.

## 데이터 모델

```ts
// src/lib/types.ts
export type MeasureType = 'time' | 'reps';

export type Exercise = {
  id: string;
  name: string;
  icon: keyof typeof Ionicons.glyphMap;
  measureType: MeasureType;
  usesWeight?: boolean;           // measureType === 'reps'일 때만 의미 있음
  weightUnit?: 'kg' | 'lb';       // usesWeight가 true일 때만
  builtin: boolean;               // true = "매달리기", 수정·삭제 불가
};

// 기존 HangRecord와 구조가 완전히 같다 — 이름만 일반화
export type TimeRecord = {
  id: string;
  measuredAt: string;
  durationMs: number;
};

export type RepsSet = {
  reps: number;
  weight?: number;                // usesWeight인 운동만
};

export type RepsRecord = {
  id: string;
  measuredAt: string;
  sets: RepsSet[];
  weightUnit?: 'kg' | 'lb';        // 저장 당시 단위 스냅샷 (요구사항 17)
};

// Settings, DEFAULT_SETTINGS, COUNTDOWN_*, BELL_INTERVAL_* 는 변경 없음
// (시간형 운동이라면 어떤 운동이든 같은 구조의 설정을 쓴다)
```

AsyncStorage 키:
- `timecheck:exercises:v1` — `Exercise[]` (신규)
- `timecheck:records:v1` / `timecheck:settings:v1` — 기존 그대로, `id: 'hang'` 운동 전용
- `timecheck:records:<id>:v1` / `timecheck:settings:<id>:v1` — 새로 추가된 시간형 운동
- `timecheck:reps:<id>:v1` — 새로 추가된 횟수·세트형 운동의 기록 (시간형과 스키마가 달라 별도 프리픽스로 구분)

## 핵심 로직

1. **운동 목록 로드 + 내장 매달리기 시딩** (요구사항 9) — `getExercises()`는 저장된 목록을 읽되, 목록에 `id: 'hang'`이 없으면(최초 실행) 자동으로 맨 앞에 추가해 저장한다. 기존 `DEFAULT_SETTINGS` 병합 패턴과 같은 방식 — 별도의 "최초 실행 마이그레이션" 스텝을 만들 필요가 없다.
   ```ts
   const BUILTIN_HANG: Exercise = {
     id: 'hang', name: '매달리기', icon: 'body-outline',
     measureType: 'time', builtin: true,
   };
   export async function getExercises(): Promise<Exercise[]> {
     const list = await readJson<Exercise[]>(EXERCISES_KEY, []);
     if (list.some((e) => e.id === 'hang')) return list;
     const seeded = [BUILTIN_HANG, ...list];
     await AsyncStorage.setItem(EXERCISES_KEY, JSON.stringify(seeded));
     return seeded;
   }
   ```

2. **운동별 저장소 키 라우팅** (요구사항 19, "마이그레이션 없는 통합") — 기록·설정 함수들이 `exerciseId`를 받아 키를 계산한다:
   ```ts
   const recordsKey = (exerciseId: string) =>
     exerciseId === 'hang' ? 'timecheck:records:v1' : `timecheck:records:${exerciseId}:v1`;
   const settingsKey = (exerciseId: string) =>
     exerciseId === 'hang' ? 'timecheck:settings:v1' : `timecheck:settings:${exerciseId}:v1`;
   ```
   `addRecord`/`updateRecord`/`removeRecord`/`getRecords`/`getSettings`/`saveSettings`는 전부 첫 인자로 `exerciseId`를 받도록 시그니처만 바뀌고, 내부 로직(직렬화 큐 포함)은 그대로다. 횟수·세트 기록은 스키마가 다르므로 `getRepsRecords(exerciseId)`/`addRepsRecord`/`removeRepsRecord`를 별도로 두되 같은 직렬화 큐를 공유한다(같은 파일 내 쓰기이므로 경합 가능성은 동일).

3. **프리셋 필터링** (요구사항 5의 자연스러운 결과) — `AddExerciseScreen`은 `PRESET_EXERCISES`에서 이미 존재하는 운동과 이름이 같은 항목을 걸러내고 보여준다. "매달리기"는 항상 존재하므로 프리셋 목록에 뜨지 않는다 — 별도의 "매달리기는 프리셋에서 제외" 특수 처리가 필요 없다.
   ```ts
   const availablePresets = PRESET_EXERCISES.filter(
     (p) => !exercises.some((e) => e.name === p.name)
   );
   ```

4. **운동 추가 검증** (요구사항 3, 5) — 이름을 trim한 뒤 1~20자 검사, 기존 `exercises` 목록과 대소문자 구분 없이 이름 중복 검사. 통과하면 `createId()`(기존 `createRecordId`를 이름만 일반화)로 id를 만들어 `Exercise` 객체를 구성하고 `addExercise()` 호출.

5. **시간형 측정 재사용** (요구사항 10) — `TimerScreen`은 지금 로직을 거의 그대로 두고 `MIN_RECORD_MS`, `useHangTimer`, 음성/벨/문구 로직 전부 유지한 채 저장소 호출부만 `exercise.id`를 전달하도록 바꾼다. 화면 타이틀도 하드코딩된 "매달리기 타이머" 대신 `${exercise.name} 타이머`로 표시한다. 즉 매달리기는 "시간형 운동의 특별 케이스"가 아니라 "시간형 운동 로직을 처음 만든 사례"였을 뿐 — 로직 변경이 아니라 매개변수화다.

6. **횟수·세트형 측정** (요구사항 12~14, 16) — `RepsScreen`은 `sets: RepsSet[]` 로컬 state(초기값 세트 1개)를 관리한다. "세트 추가"는 빈 세트를 push, 세트가 2개 이상일 때만 개별 삭제 버튼이 활성화된다(최소 1세트 보장). 각 세트 행은 `NumberStepper`로 횟수(1~999, step 1)를, `exercise.usesWeight`가 true면 숫자 `TextInput`으로 무게(소수 허용, decimal-pad 키패드)를 입력받는다. "기록 저장"을 누르면 세트 중 reps가 0인 항목이 없는지 검사 후 `RepsRecord`(measuredAt, sets, weightUnit: exercise.weightUnit)를 저장하고 세트 입력을 초기화한다. 타이머형과 달리 "저장 전 보정" 개념이 없는 단순 입력 폼이라 즉시 저장 방식이나 되돌리기 로직이 필요 없다 — 저장 버튼 한 번으로 끝난다.

7. **횟수·세트형 최고 기록** (요구사항 14) — `RecordsScreen`이 `measureType === 'reps'`일 때, 각 기록의 `sets.reduce((sum, s) => sum + s.reps, 0)`으로 총 횟수를 계산해 가장 큰 기록을 최고 기록 카드에 표시한다.

8. **기록 행 렌더링 분기** — `RecordsScreen`이 `exercise.measureType`에 따라 `RecordItem`(시간형, 기존 그대로) 또는 `RepsRecordItem`(횟수·세트형, 신규)을 선택해 렌더링한다. 두 컴포넌트 모두 날짜별 `SectionList` 그룹핑 로직은 `RecordsScreen`이 공통으로 처리하고, 각 컴포넌트는 "한 줄 렌더링" 책임만 진다.

9. **운동 이름 수정·삭제** (요구사항 7, 8) — `HomeScreen`의 각 카드에서 `!exercise.builtin`일 때만 연필 아이콘이 보인다 (매달리기는 수정·삭제 불가 — 스펙이 "사용자가 만든 운동"으로 범위를 한정했으므로). 연필을 누르면 `EditExerciseModal`이 뜨고, 이름 수정은 `updateExercise(id, { name })`(추가 시와 동일한 중복·길이 검증 재사용), 삭제는 확인 다이얼로그 후 `removeExercise(id)` + 그 운동의 기록 키(`timecheck:records:<id>:v1` 또는 `timecheck:reps:<id>:v1`, `timecheck:settings:<id>:v1`)를 함께 삭제한다.

## 의존성

추가 없음. 모달은 React Native 기본 `Modal` 컴포넌트를 쓰고, 숫자 입력은 기본 `TextInput`(`keyboardType="number-pad"`/`"decimal-pad"`)을 쓴다.

## 구현 순서

각 단계 끝에서 기존 매달리기 기능이 깨지지 않았는지(회귀) 함께 확인한다.

1. **데이터 계층** — `types.ts`에 `Exercise`/`MeasureType`/`RepsSet`/`RepsRecord` 추가, `HangRecord`→`TimeRecord` 이름 변경. `storage.ts`에 운동 CRUD + `exerciseId` 매개변수화 + 횟수·세트 기록 함수 추가. `exercisePresets.ts` 작성. `menu.ts` 삭제. 타입 체크.
2. **홈 화면 동적 목록 전환** — `HomeScreen`이 `getExercises()`로 목록을 그려 지금과 똑같이 매달리기 하나만 보이는지 확인 (첫 실기기 회귀 확인 지점).
3. **운동 추가 흐름** — `AddExerciseScreen` + `App.tsx` 라우팅. 프리셋 탭/직접 입력으로 운동을 추가하고 홈에 나타나는지, 중복 이름이 막히는지 확인.
4. **시간형 타이머 일반화** — `TimerScreen`을 `exercise` prop 기반으로 바꾸고 `ExerciseScreen`(구 `HangScreen`) 경유로 연결. 매달리기가 여전히 정상 동작(회귀)하고, 새로 추가한 시간형 운동(예: 플랭크)도 독립적으로 동작하는지 확인.
5. **횟수·세트형 측정** — `RepsScreen` 작성, 세트 추가·삭제·저장 확인. 무게 사용 운동에서 단위 표시까지 확인.
6. **기록 화면 일반화** — `RecordsScreen`을 `exercise` 기반으로 바꾸고 `RepsRecordItem` 추가. 매달리기 기록이 여전히 보이는지(회귀), 새 운동들의 기록이 서로 섞이지 않는지 확인.
7. **운동 관리** — `EditExerciseModal`로 이름 수정·삭제. 매달리기에는 편집 버튼이 안 보이는지 확인.
8. `npx tsc --noEmit` + 실기기 전체 시나리오 확인 → `/qa`.

## QA 수정 내역 (2026-07-25)

`/qa`에서 발견된 항목을 반영:

- **프리셋 표시 개수**: 매달리기는 항상 필터링되므로 5개를 정의하면 화면엔 4개만 보인다. `exercisePresets.ts`에 프리셋을 6개(런지 추가)로 늘려 필터링 후에도 항상 5개 이상 보이도록 함.
- **이름 중복 검사 대소문자**: `AddExerciseScreen`/`EditExerciseModal` 모두 `toLocaleLowerCase()` 비교로 통일 (설계 의도와 일치).
- **운동 목록 로드 레이스**: `AddExerciseScreen`에 `namesLoaded` 플래그 추가 — 기존 운동 목록을 다 읽기 전에는 프리셋을 아예 보여주지 않고, 저장도 막는다. 로드 전 짧은 창에서 매달리기 프리셋이 깜빡이거나 중복 생성될 수 있던 문제 제거.
- **`getExercises()` 방어 코드**: 다른 저장 함수들과 달리 `Array.isArray` 가드가 없어 손상된 데이터에서 크래시 가능성이 있었음 — 가드 추가.
- **`RepsScreen` 세트 많을 때 저장 버튼 도달 불가**: 고정 레이아웃이라 세트가 6~7개를 넘으면 화면 밖으로 밀림 — `ScrollView`(+`KeyboardAvoidingView`)로 감싸 세트 목록만 스크롤되고 "기록 저장" 버튼은 항상 하단에 고정되도록 재구성. 무게 사용 시 가로 폭 초과 대비 `setRow`에 `flexWrap` 추가. 횟수 입력에 `editable` 옵션도 추가(길게 누를 필요 없이 탭 입력 가능).
- **`EditExerciseModal`에 무게 옵션 없음**: 요구사항 15("추가·수정" 모두)를 만족하도록 수정 모달에도 횟수·세트형 운동 한정으로 "무게 기록 사용" 스위치 + kg/파운드 세그먼트 추가.
- **프리셋 탭 → 확인 단계 유지**: `/qa`에서 스펙 요구사항 2("탭하면 바로 추가")와 요구사항 4("바꿀 수 있다")의 충돌을 발견했고, 사용자가 지금의 확인 단계(탭 → 폼에 채움 → "운동 추가" 버튼) 방식을 유지하기로 확정 — 스펙 문서 쪽을 실제 동작에 맞게 수정함.
